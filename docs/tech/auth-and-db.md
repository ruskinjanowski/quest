# Quest — Auth & Database

## Stack

- **Database**: Neon Postgres (`DATABASE_URL`), accessed over HTTP.
- **ORM**: Drizzle (`src/db/schema/`, `src/db/index.ts`, `drizzle.config.ts`).
- **Auth**: Better Auth with the Drizzle adapter (`src/lib/auth.ts`,
  `src/app/api/auth/[...all]/route.ts`).

## Environment variables

Copy `.env.example` to `.env.local`.

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Neon connection string, with `sslmode=require&channel_binding=require`. |
| `BETTER_AUTH_SECRET` | 32+ chars. `openssl rand -base64 32`. |
| `BETTER_AUTH_URL` | Base URL of the app (`http://localhost:3000` locally). Ignored on Vercel — see below. |
| `NEXT_PUBLIC_SITE_URL` | Canonical URL, used as the auth fallback and for metadata. |
| `DEMO_USER_EMAIL` / `DEMO_USER_PASSWORD` | Seeded demo account; shown on the sign-in screen when set. |
| `ALLOW_DEMO_RESET` | `"true"` enables the Settings → Reset demo data action. |

## Drizzle workflow

Schema lives in `src/db/schema/`, one module per table, re-exported from
`src/db/schema/index.ts` — which is what `drizzle.config.ts` points at. Adding a
table means adding a module and a re-export line.

```bash
npm run db:generate
```

```bash
npm run db:migrate
```

```bash
npm run db:studio
```

Migrations are committed under `drizzle/`. `0000_init.sql` creates the auth
tables plus `quests` and `tasks`. `0002` dropped `time_entries` when the timer
came out, moving time onto the task itself.

The connection in `src/db/index.ts` is created lazily, so importing the module
never requires `DATABASE_URL` — `next build` and any future unit test can load
the code without a database.

## Seeding

```bash
npm run db:seed
```

Creates the demo account if missing (password hashed with Better Auth's own
hasher, so it signs in through the normal flow) and replaces **only that user's**
data with roughly four weeks of history across four quests plus admin. The
dataset is generated from a seeded PRNG, so every reseed tells the same story
and the Loom can be re-shot without the numbers moving.

The same routine backs Settings → *Reset demo data*, scoped to the calling user.

## Better Auth workflow

- **Server-side session**: `requireUser()` / `getCurrentUser()` from
  `src/lib/session.ts`. Both wrap `auth.api.getSession` and are deduped per
  request with `cache()`.
- **Client-side**: `authClient`, `useSession` from `src/lib/auth-client.ts`,
  wired to `/api/auth/[...all]`.
- The `nextCookies()` plugin is last in the plugin list so sign-in from a server
  action can set the session cookie.

Email + password only, on purpose. Email verification, password reset, magic
links and OAuth are deferred to the 3-month plan.

### Origins on Vercel

Better Auth rejects any POST whose `Origin` header isn't the base URL or in
`trustedOrigins` — a 403 `INVALID_ORIGIN`, which shows up in the UI as
*"Invalid origin"* under the sign-in form. Preview deployments get a new
hostname on every push, so the origin list is built at runtime from
`VERCEL_PROJECT_PRODUCTION_URL`, `VERCEL_BRANCH_URL` and `VERCEL_URL` (system
variables Vercel injects for free). When those are present the production
domain also becomes the base URL, so a stale `BETTER_AUTH_URL` in the Vercel
project settings can't take the deployed app down. Locally, nothing changes:
`BETTER_AUTH_URL` is still the base URL.

## Data model

| Table | Notes |
|---|---|
| `users`, `sessions`, `accounts`, `verifications` | Better Auth core. `users.id` is a real uuid generated by Postgres, so product tables can reference it. |
| `quests` | `lifecycle` (active/completed/archived) decides whether a quest counts; `health` (on_track/at_risk/off_track/achieved) is the display chip. Two different questions, two columns. |
| `tasks` | `quest_id IS NULL` **is** the Admin bucket — there is no admin quest row. `planned_date IS NULL` means backlog. `estimate_minutes` is `PLANNED`, `actual_minutes` is `ACTUAL`; every split reports `COALESCE(actual, estimate)` over *done* tasks. `horizon` only means anything while `planned_date` is null. |

Deleting a quest sets its tasks' `quest_id` to null — they move to Admin rather
than taking their history with them.
